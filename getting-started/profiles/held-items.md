# Held-item Visuals

The visual state belongs to the profile and is independent of the arm animation.
Only Armature's displayed copy changes; the player's inventory item and its
components are left intact. The same section is accepted in legacy profiles
that use `model.name`.

An arc can reuse its source model's `minecraft:using_item` and
`minecraft:use_duration` branches. The vanilla arc changes at 13 and 18 ticks:

```yaml
bow:
  match:
    item: minecraft:bow
  model:
    name: bow_arms
    held-item:
      mode: source
```

For a trident or shield whose arm animation already presents the action, keep
the rest appearance even while the player uses the item:

```yaml
trident:
  match:
    item: minecraft:trident
  model:
    name: trident_arms
    held-item:
      mode: static
```

Use `mode: source` for that trident or shield when the pack's use branches are
wanted. The selection is generic: the source item definition is read after
the resource-pack priority and overlay resolution. Conditions unrelated to use
remain in the item model for Minecraft to evaluate.

```yaml
shield:
  match:
    item: minecraft:shield
  model:
    name: shield_arms
    held-item:
      mode: static # change to source to display the pack's blocking model
```

For custom models, rules are checked in file order. Each `model` refers to an
existing `assets/<namespace>/models/<path>.json` in the effective pack. Missing
references fail pack generation instead of publishing a broken state:

```yaml
custom_bow:
  match:
    item: itemsadder:custom_bow
  model:
    name: custom_bow_arms
    held-item:
      mode: rules
      default: original
      rules:
        - when: item.use-ticks >= 18t
          model: mypack:item/custom_bow_pulling_2
        - when: item.use-ticks >= 13t
          model: mypack:item/custom_bow_pulling_1
        - when: item.using == true
          model: mypack:item/custom_bow_pulling_0
```

`item.using` and `item.use-ticks` refer to the hand being rendered. `original`
keeps the ordinary item model as the fallback. The rules select an item-model
alias generated by Armature; they do not change gameplay or use duration.

To keep the vanilla item visible normally and show Armature only for selected
events, make the render allow-list explicit and keep hand hiding enabled:

```yaml
model:
  name: baseball_bat
  hide-vanilla-hand: true
  render-events: [player:attack]
```

Entries may be action ids such as `swing` or namespaced signals such as
`player:attack`. The allow-list controls model visibility; the matching rule
under `animations.actions` still controls which clip plays. PacketEvents is
required for conditional first-person hand masking.

For a model that stays loaded while the vanilla item remains visible during
normal movement, move hand hiding to the rules:

```yaml
model:
  name: baseball_bat
  hide-vanilla-hand: true

animations:
  movement:
    - when: player.speed >= 0
      hide-vanilla-hand: false
      animation: base
  actions:
    - trigger: player:attack
      hide-vanilla-hand: true
      animation: attack_1
```

The active action rule has priority over the selected movement rule. A rule
without `hide-vanilla-hand` inherits from the next level, then from
`model.hide-vanilla-hand`. This option controls hand masking only;
`model.render-events` remains the separate model-visibility allow-list.

`animations` is a container, not an animation registry. The modern loader
rejects `animations.definitions`, top-level `actions`, top-level `triggers`,
and `mode` under action rules. Animations are declared beside the rule using
them.

An accepted `item:unequip` action keeps its outgoing model alive until the
authored clip finishes, including its playback speed. Further slot changes
do not close earlier outgoing models. Returning to a profile during its
unequip reclaims the same model instance and blends from its current pose
into equip or the normal movement cycle, using the incoming animation's
blend settings. Profiles sharing a model asset retain separate instances.
Without an accepted unequip animation, removal is immediate.

The optional Fabric client requires protocol 9 for overlapping hotbar
presentations; update its JAR together with the plugin.

## Transition ownership

The displayed copy belongs to the presentation session. With
`render.dynamic-items.defer-until-equipped`, an outgoing model retains its
resolved item definition and item components through unequip/deferred action.
The incoming equip receives current inventory items. This changes presentation
only, never the real item, use duration, damage, ammo or weapon state.

Verify source/static/rules selection using the **provider's effective final pack**,
including active overlays. A definition visible in a standalone test ZIP may
not be the definition delivered by the provider.
